# راهنمای عملیاتی ایجنت‌ها و مشارکت‌کنندگان Lottorito

**شناسه سند:** LOT-AGENT-001 | **نسخه:** ۱.۰.۰ | **وضعیت:** استاندارد عملیاتی نگهداری‌شده؛ تأیید محصول مستقل است

## هدف
نقطه ورود کم‌هزینه از نظر Context برای ایجنت‌های هوش مصنوعی، مشارکت‌کنندگان انسانی، بازبین‌ها و اتوماسیون‌ها. هدف کاهش کشف تکراری بدون تضعیف شواهد، ایمنی و هم‌ارزی دوزبانه است. این راهنما جایگزین مشخصات دامنه‌ها نیست.

## ترتیب مطالعه
۱. AGENTS.md در ریشه مخزن — قواعد اجباری ایمنی و گردش کار.
۲. همین راهنما — مسیریابی وظیفه و حداقل Context.
۳. docs/fa/engineering/project-status.md — خط مبنای تأییدشده و موانع.
۴. docs/fa/engineering/decision-register.md — وضعیت تصمیم‌ها و انتخاب‌های باز مالک.
۵. سند مرجع دامنه مرتبط با وظیفه.
۶. نسخه انگلیسی متناظر هنگام ویرایش یا بازبینی مستند دوزبانه.

همه اسناد را پیش‌فرض بارگذاری نکنید؛ فقط مرجع مرتبط و وابستگی‌های آن را بخوانید.

## واژگان شواهد
- **Proposed / پیشنهادی:** گزینه مستند؛ هنوز برای پیاده‌سازی تصویب نشده.
- **Accepted / پذیرفته‌شده:** صریحاً توسط مالک یا حاکمیت مجاز تصویب شده.
- **Implemented / پیاده‌سازی‌شده:** کد یا تنظیمات در شاخه/Commit مشخص وجود دارد.
- **Verified / راستی‌آزمایی‌شده:** تست یا کنترل تعریف‌شده با شواهد ثبت‌شده موفق شده.
- **Released / منتشرشده:** انتشار در محیط مشخص صریحاً تأیید و انجام شده.
- **Blocked / مسدود:** پیش‌نیاز مشخصی مانع پیشرفت است.
- **Superseded / جایگزین‌شده:** تصمیم جدیدتر جایگزین شده؛ تاریخچه حفظ و به تصمیم جدید لینک می‌شود.

وجود سند، موفقیت نوشتن فایل، Draft بودن PR یا یادآوری تأییدنشده مجوز ارتقای وضعیت نیست.

## چرخه اجباری وظیفه
۱. جهت‌یابی: منابع حداقلی را بخوانید؛ شاخه، PR، فایل‌ها و تغییرات اخیر را بررسی کنید.
۲. جست‌وجو پیش از ایجاد: سند، Issue، کد، تست و تصمیم مشابه را بیابید.
۳. طبقه‌بندی: دستور مالک، شواهد تأییدشده، پیشنهاد، فرض و پرسش باز را جدا کنید.
۴. برنامه‌ریزی: فایل‌ها، وابستگی‌ها، معیار پذیرش و ریسک‌ها را مشخص کنید.
۵. تغییر: از شاخه اختصاصی و Commitهای منسجم و قابل‌بازبینی استفاده کنید.
۶. هم‌ترازی زبان‌ها: فارسی و انگلیسی در همان PR به‌روزرسانی شوند؛ اعداد، فرمول‌ها، وضعیت‌ها، محدودیت‌ها، مثال‌ها و معیار پذیرش هم‌معنا بمانند.
۷. اعتبارسنجی: همه فایل‌های تغییرکرده را مجدداً بخوانید؛ کنترل‌های موجود را اجرا و موارد اجرا‌نشده را صادقانه گزارش کنید.
۸. تحویل: شاخه، Commit/PR، فایل‌ها، تصمیم‌ها، تست‌ها، محدودیت‌ها، پرسش‌های باز و اقدام بعدی را اعلام کنید.

## صرفه‌جویی در زمان و Token
- وقتی سند نگهداری‌شده پاسخ می‌دهد، تاریخچه کامل گفتگو را دوباره نخوانید.
- از وضعیت پروژه و Decision Register شروع کنید؛ فقط سند/بخش مرتبط را دریافت کنید.
- شناسه پایدار، واژگان canonical و قالب‌های موجود را دوباره استفاده کنید.
- مشخصات کامل را در README، فهرست‌ها، Issueها و Promptها تکرار نکنید؛ به مرجع canonical لینک دهید.
- تحویل کوتاه شامل هدف، خط مبنا، فایل‌ها، شواهد، موارد حل‌نشده و گام بعدی باشد.
- در صورت از دست رفتن Context از GitHub بازیابی کنید: AGENTS.md ← وضعیت پروژه ← Decision Register ← مشخصات مرتبط ← شواهد PR/Commit.
- فقط پرسشی را از مالک بپرسید که مانع تصمیم مهم است؛ پاسخ مصوب ثبت‌شده را دوباره نپرسید.

## مرز اختیار
ایجنت‌ها در محدوده مجاز می‌توانند بررسی، تحلیل، پیش‌نویس، شاخه‌سازی و Draft PR ایجاد کنند. بدون اجازه صریح مالک، Merge، Deploy، تغییر تنظیمات مخزن، چرخش/افشای Secret، ایجاد هزینه بیرونی، تماس با شریک یا عملیات مخرب ممنوع است.

هیچ مقدار تجاری پیشنهادی، حوزه قضایی، رفتار Provider، قاعده پرداخت یا محدوده محصول بدون تأیید مستند نباید به invariant اجرایی تبدیل شود.

## توقف امنیتی و مالی
در صورت احتمال اثر مالی تکراری، دسترسی بین Tenantها، دستکاری دفترکل، تعدیل غیرقابل‌ردیابی، پرداخت غیرمجاز، افشای Secret/اطلاعات شخصی یا فعالیت بدون بررسی حوزه قضایی، توقف و ارجاع الزامی است. تاریخچه مالی افزایشی است و اصلاحات با اسناد معکوس/تعدیلی مرتبط انجام می‌شوند.

## نگهداری مستندات
هر سند مرجع باید شناسه، نسخه، وضعیت، مسئول بازبینی و همتای دوزبانه داشته باشد. با تغییر دامنه یا وضعیت تصمیم، فهرست و Decision Register را به‌روز کنید. فقط مثال ساختگی به‌کار ببرید. Credential، داده واقعی مشتری/بازیکن و خروجی Production وارد Git نشود.
