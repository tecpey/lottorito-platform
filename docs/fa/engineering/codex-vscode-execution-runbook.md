# راهنمای اجرای پروژه با Codex، VS Code و GitHub

**شناسه سند:** LOT-ENG-002  
**نسخه:** 0.1.0  
**وضعیت:** راهنمای عملیاتی پیشنهادی؛ نیازمند تأیید مالک برای انتخاب ابزارها و سیاست‌های اجرایی  
**نسخه متناظر:** `docs/en/engineering/codex-vscode-execution-runbook.md`

## 1. هدف

این سند روش واحدی برای ادامه توسعه Lottorito از طریق مخزن GitHub، Codex ابری و محیط VS Code تعریف می‌کند. هدف این است که هر محیط یا ایجنت از یک وضعیت مشترک و قابل اثبات ادامه دهد، کار تکراری نسازد و تغییرات هم‌زمان یکدیگر را از بین نبرد.

## 2. منبع حقیقت

ترتیب اعتبار اطلاعات:

1. وضعیت فعلی GitHub: commit، branch، فایل‌ها، Issueها، PRها و نتایج CI.
2. اسناد تأییدشده در شاخه‌ای که PR آن پذیرفته و ادغام شده است.
3. تصمیم‌های ثبت‌شده در ADR و تصمیم‌های تجاری تأییدشده مالک محصول.
4. Issueهای باز به‌عنوان کار برنامه‌ریزی‌شده، نه قابلیت انجام‌شده.
5. گفتگوها، خلاصه‌ها و خروجی‌های ایجنت فقط سرنخ هستند و جایگزین شواهد مخزن نمی‌شوند.

هیچ ایجنتی نباید صرفاً بر اساس حافظه گفتگو یا توضیح قبلی فرض کند یک فایل، تست، API یا قابلیت وجود دارد.

## 3. نقطه ورود اجباری ایجنت‌ها

در ابتدای هر نشست کاری:

1. شاخه و commit فعلی را از GitHub بررسی کن.
2. `AGENTS.md` و این Runbook را بخوان.
3. `docs/en/engineering/project-status.md` و نسخه فارسی متناظر را بخوان.
4. Issueها و PRهای باز و مرتبط را بررسی کن.
5. اسناد دامنه مربوط به وظیفه را در هر دو زبان بخوان.
6. وجود فایل، کلاس، endpoint، migration و تست مشابه را جست‌وجو کن.
7. قبل از تغییر، برنامه کوتاه شامل فایل‌های هدف، خطرها و تست‌ها بنویس.

اگر وضعیت محلی با GitHub فرق دارد، ابتدا اختلاف را گزارش و حل کن؛ روی وضعیت نامعلوم کدنویسی نکن.

## 4. تقسیم مسئولیت محیط‌ها

### GitHub

- مرجع اصلی تاریخچه، کد، مستندات، Issue و PR است.
- هر تغییر قابل بازبینی باید در branch مستقل ثبت شود.
- شاخه `main` خط مبنای پایدار است؛ توسعه مستقیم روی آن انجام نشود.
- PR باید هدف، محدوده، تصمیم‌ها، فایل‌های تغییرکرده، تست‌ها، ریسک‌ها و موارد انجام‌نشده را توضیح دهد.

### Codex ابری

- برای کارهای مستقل و قابل واگذاری استفاده شود؛ هر مأموریت باید Issue، محدوده، معیار پذیرش و branch مشخص داشته باشد.
- Codex باید قبل از تغییر، وضعیت GitHub را تازه‌سازی و راهنمای ایجنت را بخواند.
- خروجی آن PR قابل بازبینی است، نه مجوز Merge یا Deploy.
- دو عامل نباید هم‌زمان روی یک فایل یا یک branch مشترک بدون هماهنگی بنویسند.

### VS Code و Codex محلی

- برای توسعه تعاملی، اجرای تست‌ها، اشکال‌زدایی و بررسی تغییرات محلی استفاده شود.
- قبل از شروع، branch کاری را با آخرین وضعیت GitHub همگام کن.
- بعد از هر واحد کاری، تست‌های مرتبط را اجرا و نتیجه واقعی را ثبت کن.
- پیش از Push، diff و فایل‌های ناخواسته، secretها و داده‌های واقعی را بررسی کن.
- تغییرات محلی باید به branch و PR مشخصی برسند؛ فایل‌های محلیِ بدون commit مرجع قابل اتکای ادامه کار نیستند.

## 5. قرارداد API و اسرار

- هیچ API key، token، password، webhook secret، private key یا credential در Git، Issue، PR، log یا مستندات نمونه ثبت نشود.
- دسترسی API فقط از طریق اتصال رسمی و مجوزهای حداقلی لازم فراهم شود.
- برای اجرای محلی از فایل محیطی خارج از Git مانند `.env.local` استفاده شود و فایل نمونه فقط نام متغیرها و توضیح غیرمحرمانه را داشته باشد.
- برای محیط ابری، secretها در قابلیت امن مدیریت Secrets همان سرویس نگهداری شوند؛ هرگز در prompt یا فایل پروژه قرار نگیرند.
- دسترسی نوشتن به GitHub به معنی دسترسی به سرور تولید، دیتابیس، حساب شریک یا مجوز Deploy نیست.
- هر دسترسی جدید باید به سرویس، محدوده و اقدام مشخص محدود باشد و پیش از استفاده، دسترسی واقعی بررسی شود.

## 6. چرخه استاندارد هر کار

1. انتخاب Issue موجود؛ اگر وجود ندارد، پس از جست‌وجوی تکراری‌ها Issue بساز.
2. ثبت معیار پذیرش و وابستگی‌ها.
3. ایجاد branch از آخرین `main` یا branch وابستگی تأییدشده.
4. بررسی اسناد و کد مرتبط؛ طرح تغییر را پیش از پیاده‌سازی مشخص کن.
5. پیاده‌سازی کوچک و محدود.
6. اجرای تست‌های واحد، یکپارچه، قراردادی، امنیتی یا E2E متناسب با ریسک.
7. به‌روزرسانی مستندات فارسی و انگلیسی در همان PR.
8. بررسی diff، secret scanning، lint، typecheck و تست‌های مرتبط.
9. ایجاد یا به‌روزرسانی PR و ثبت SHA و شواهد.
10. رسیدگی به review و CI؛ فقط پس از تأییدهای لازم، Merge توسط فرد مجاز.

## 7. قاعده جلوگیری از دوباره‌کاری و تداخل

- پیش از ساخت فایل یا Issue جدید، کل مخزن و کارهای باز را جست‌وجو کن.
- هر کار یک شناسه پایدار داشته باشد و وضعیت آن در Issue و سند وضعیت منعکس شود.
- وضعیت‌ها فقط یکی از این موارد باشند: Proposed، In Progress، Blocked، In Review، Verified، Done یا Deferred.
- «فایل ساخته شد» با «محتوا بازبینی شد»، «تست شد» یا «تأیید شد» یکسان نیست.
- کارهای نیمه‌تمام PR دیگر را بدون بررسی و هماهنگی کپی یا بازنویسی نکن.
- اگر PR قبلی شامل سند موردنیاز است، همان PR را بررسی و تکمیل کن؛ نسخه موازی نساز.
- تغییرات یک وظیفه باید در یک PR کوچک و قابل ردیابی جمع شوند؛ از commitهای مبهم و تغییرات نامرتبط اجتناب کن.

## 8. دروازه‌های پیش از شروع کدنویسی محصول

قبل از انتخاب stack و ساخت اسکلت اجرایی باید این موارد روشن شوند:

- محدوده MVP و نقش‌های کاربری و مدیریتی
- قواعد تجاری تأییدشده پایلوت و موارد باز
- ADRهای runtime، API framework، database، migrations، queue، auth و testing
- قرارداد canonical event و قرارداد واقعی شریک؛ موارد نامعلوم به‌صورت adapter interface و mock صریح باقی بمانند
- مدل مالی، ارز، دقت اعشار، چرخه posting، reversal و reconciliation
- الزامات امنیت، tenant isolation و حریم خصوصی
- معماری تست و CI و معیارهای پذیرش

تا پیش از دریافت قرارداد واقعی شریک، هیچ endpoint، payload، signature scheme یا رفتار مالی اختصاصی شریک را حدس نزن.

## 9. قالب گزارش تحویل هر ایجنت

هر تحویل باید شامل موارد زیر باشد:

- Issue و هدف
- branch و PR
- commit SHA دقیق
- فایل‌های ایجاد/ویرایش‌شده
- تصمیم‌های اتخاذشده و ارجاع ADR
- تست‌های اجراشده با فرمان و نتیجه واقعی
- تست‌های اجرا‌نشده و علت
- ریسک‌ها و محدودیت‌ها
- موارد باز و وابستگی‌ها
- نقطه شروع دقیق برای ایجنت بعدی

## 10. مرز مجوزها

ایجنت‌ها می‌توانند در محدوده دسترسی واقعی، مستندات و کد را در branch کاری تغییر دهند و PR بسازند. Merge نهایی، Deploy عملیاتی، تغییر دسترسی/Visibility، تغییر یا حذف داده، استفاده از credential تولیدی و هر اقدام مالی واقعی نیازمند مجوز جداگانه است.

## 11. وضعیت فعلی

این Runbook در شاخه `docs/codex-execution-baseline` تهیه شده و هنوز در `main` ادغام نشده است. وجود این سند به معنی اتصال یا پیکربندی موفق Codex Cloud، VS Code، API، Secrets، CI یا محیط اجرا نیست. این اتصال‌ها باید جداگانه و با شواهد واقعی تأیید شوند.


## 12. تفکیک Codex، Cloud و OpenAI API

این سه مفهوم را یکی فرض نکن:

- **ورود به Codex:** مستندات رسمی، ورود با حساب ChatGPT یا استفاده از API key را برای کلاینت‌های پشتیبانی‌شده توضیح می‌دهند. روش فعال در کلاینت نصب‌شده باید در همان محیط بررسی شود.
- **Codex Cloud:** اجرای task روی محیط مدیریت‌شده ابری است. ابتدا باید repository، ابزارها، dependencyها، دسترسی GitHub و تنظیمات محیط آماده و منتشر شوند. هر task محیط کاری جداگانه دارد؛ برای حفظ کار باید تغییرات مهم commit شوند. بازکردن task جدید، تغییرات commit‌نشده task قبلی را بازیابی نمی‌کند.
- **OpenAI API برای محصول:** کلید API برنامه Lottorito برای فراخوانی مدل‌ها/سرویس‌های OpenAI است؛ این کلید با مجوز GitHub یا ورود Codex یکی نیست و نباید در مخزن ثبت شود.
- **OpenAI Developer Docs MCP:** سرور `https://developers.openai.com/mcp` فقط مستندات رسمی را جست‌وجو و می‌خواند؛ خودش درخواست API محصول را اجرا نمی‌کند.

### مسیر عملی پیشنهادی
1. در VS Code افزونه رسمی Codex را نصب و با روش مجاز حساب/کلید وارد شو.
2. مخزن `tecpey/lottorito-platform` را در VS Code باز کن و مطمئن شو branch و SHA با GitHub هماهنگ‌اند.
3. در صورت استفاده از Codex Cloud، محیطی برای همین repository بساز، dependencyها و ابزارها را تعریف کن و دسترسی GitHub را جداگانه آزمایش کن.
4. یک task آزمایشی فقط‌مستنداتی از Issue #16 اجرا کن؛ خروجی باید branch و PR قابل بازبینی باشد.
5. پس از اثبات این مسیر، اولین task کدنویسی محصول را از Issueهای موجود و پس از تکمیل ADRها انتخاب کن.
