# قرارداد پاکت رویداد canonical و معنای تحویل

**شناسه سند:** LOT-EVENT-001 | **نسخه:** ۰.۱.۰ | **وضعیت:** قرارداد پیشنهادی پلتفرم؛ API پیاده‌سازی‌شده نیست

## ۱. هدف
پاکت مستقل از Provider برای رویدادهایی تعریف می‌کند که از مرز دامنه، Tenant، شریک یا پردازش غیرهمزمان عبور می‌کنند. Schema Payload دامنه‌ای در مالکیت Bounded Context مربوط است و جداگانه نسخه‌بندی می‌شود.

## ۲. سه شناسه که هرگز نباید یکی فرض شوند
- **Source Event ID:** هویت پیام/واقعیت در منبع و فضای نام همان منبع.
- **Economic Effect ID:** هویت یک پیامد تجاری/اقتصادی موردنظر پس از احراز شرایط و ارزیابی سیاست.
- **Journal Entry ID:** هویت ثبت حسابداری در دفترکل.

یک رویداد منبع ممکن است هیچ اثر اقتصادی، یک اثر یا چند اثر کنترل‌شده ایجاد کند. اثر ممکن است غیرمالی باشد یا به چند سند دفترکل نیاز داشته باشد. Replay همان رویداد نباید اثر اقتصادی را تکرار کند؛ اصلاح حسابداری با سند معکوس/تعدیلی مرتبط انجام می‌شود، نه استفاده مجدد از Event ID یا ویرایش دفترکل.

## ۳. پاکت canonical

| فیلد | معنا |
|---|---|
| event_id | شناسه یکتای تغییرناپذیر رکورد رویداد در پلتفرم |
| source_system | هویت احرازشده منبع/Provider |
| source_event_id | شناسه پایدار رویداد منبع با فضای نام منبع |
| event_type | نام رویداد با دامنه مشخص |
| schema_version | نسخه قرارداد Payload |
| tenant_id | محدوده معتبر Tenant استخراج‌شده از اتصال/عضویت احرازشده |
| product_domain | Affiliate، Lottery یا دامنه مشترک صریح پلتفرم |
| aggregate_type / aggregate_id | Aggregate دامنه‌ای متأثر |
| occurred_at | زمان رخداد اعلام‌شده منبع با حفظ Offset/منطقه |
| received_at | Timestamp دریافت در پلتفرم |
| recorded_at | Timestamp ذخیره پایدار در پلتفرم |
| actor_type / actor_id | کاربر، Service Principal، Provider یا Actor سیستمی |
| correlation_id | ردیابی سرتاسری درخواست/گردش‌کار |
| causation_id | رویداد/فرمان بلافاصله مسبب این رویداد |
| idempotency_key | کلید پایدار برای جلوگیری از عملیات/اثر تکراری |
| source_reference | ارجاع provenance قابل اعتبارسنجی |
| raw_payload_hash | Hash تمامیت شواهد خام نگهداری‌شده، در صورت وجود |
| payload | Payload دامنه‌ای اعتبارسنجی‌شده، حداقلی و نرمال‌شده |
| classification | طبقه‌بندی حساسیت و نحوه نگهداری داده |

Tenant باید از تنظیمات معتبر اتصال/نشست استخراج شود. فیلد Tenant در Payload فقط ادعای سازگاری است، نه مرجع اختیار.

## ۴. معنای زمان‌ها
Timestampهای جداگانه حفظ شوند:
- occurred_at: زمانی که منبع اعلام می‌کند رویداد رخ داده است.
- received_at: زمان دریافت در پلتفرم.
- recorded_at: زمان ذخیره پایدار در پلتفرم.
- recognized_at / posted_at: زمان شناسایی یا ثبت اثر طبق سیاست دامنه/مالی، در صورت کاربرد.

زمان دریافت را جایگزین زمان منبع یا شناسایی مالی نکنید. Instantها به UTC ذخیره شوند و Offset/منطقه اصلی در صورت نیاز قراردادی/ممیزی حفظ شود.

## ۵. چرخه دریافت
مراحل پیشنهادی: RECEIVED ← AUTHENTICATED ← VALIDATED ← NORMALIZED ← ACCEPTED_FOR_PROCESSING ← PROCESSED؛ همراه با وضعیت‌های صریح REJECTED، QUARANTINED و RETRY_PENDING. در صورت الزام قرارداد انتقال، پیش از تأیید پذیرش پایدار، دریافت و شواهد ذخیره شوند.

احراز اصالت، اعتبارسنجی Schema، احراز شرایط تجاری و ثبت مالی مراحل جدا هستند. پیام احرازشده الزاماً رویداد تجاری معتبر نیست؛ رویداد معتبر نیز الزاماً کمیسیون‌پذیر یا قابل شناسایی مالی نیست.

## ۶. تحویل و Idempotency
تحویل را At-least-once فرض کنید، مگر قرارداد انتقال راستی‌آزمایی‌شده خلاف آن را ثابت کند. Inbox پایدار با کلید فضای نام منبع و source_event_id و Idempotency اختصاصی عملیات استفاده شود. یکتایی در نقطه ایجاد اثر تجاری به‌صورت تراکنشی اعمال شود. فقط پس از دریافت پایدار ACK دهید؛ Retry هویت اصلی را حفظ کند. Backoff محدود، jitter، Dead-letter/Quarantine و Replay کنترل‌شده لازم‌اند. Replay باید هویت منبع اصلی را حفظ و Actor/دلیل Replay را ثبت کند.

## ۷. اصلاح و رویداد دیررس
اصلاحیه رویداد جدیدی است که به رویداد اصلی و دلیل اصلاح ارجاع می‌دهد. Reversal رویداد تجاری/اقتصادی جدیدی است که به اثر اصلی و سند دفترکل اولیه متصل است. تغییر سیاست به‌طور پیش‌فرض از آینده اعمال می‌شود، مگر فرایند Recalculation صریح و مجاز خلاف آن را تعیین کند. دیر رسیدن، occurred_at را تغییر نمی‌دهد؛ زمان دریافت جدا ثبت و قواعد دوره/شناسایی اعمال شوند.

## ۸. امنیت و حریم خصوصی
منبع احراز شود؛ امضا/Timestamp در صورت پشتیبانی اعتبارسنجی و Replay مسدود شود؛ اندازه و Schema Payload محدود؛ Secretها Redact؛ داده شخصی حداقلی؛ شواهد نگهداری‌شده رمزنگاری؛ دسترسی Payload خام محدود؛ Retention و Legal Hold تعریف شود. provenance و نتیجه اعتبارسنجی ثبت شوند.

## ۹. مشاهده‌پذیری و عملیات
تعداد دریافت/پذیرش/رد/تکراری/دیررس/قرنطینه، تأخیر پردازش، عمر Retry، عمق Dead-letter، نرخ خطای هر Tenant/Provider و شکاف تطبیق اندازه‌گیری شوند. برای Backlog پایدار، امضای نامعتبر، موج Duplicate، نتیجه نامشخص و مغایرت اثر اقتصادی هشدار ایجاد شود. Replay ایمن و Runbook اپراتور لازم است.

## ۱۰. معیارهای پذیرش
- تحویل تکراری یک رکورد Source Event و بدون Economic Effect تکراری ایجاد کند.
- Source Event، Economic Effect و Journal Entry به‌صورت دوطرفه قابل ردیابی باشند.
- هویت Tenant سمت سرور حل و مغایرت رد شود.
- معنای مستقل Timestampها حفظ شود.
- اصلاح و Reversal تاریخچه اصلی را حفظ کنند.
- تکامل Schema نسخه‌بندی و از نظر سازگاری آزموده شود.
- رفتار شکست/Retry/Replay/Concurrency تست شود.
- داده شخصی و شواهد خام تابع کنترل دسترسی و Retention باشند.

## ۱۱. تصمیم‌های باز
انتخاب Transport، قرارداد نام‌گذاری رویداد، Schema Registry، Payload canonical هر دامنه، مدت Retention، الگوریتم Hash/Signature، Partitioning، مجوز Replay، انواع رویداد مجاز برای ایجاد اثر اقتصادی و سیاست شناسایی مالی.
