# مدل تهدید امنیتی Lottorito

**شناسه سند:** LOT-SEC-TM-001 | **نسخه:** ۰.۱.۰ | **وضعیت:** خط مبنای پیشنهادی؛ نیازمند بازبینی امنیت، محصول و مالک

## ۱. محدوده و محدودیت
این سند پیشنهاد مدل تهدید سطح سامانه برای پلتفرم جهانی و چندمستاجری Affiliate & Agent و Lottery است. تست نفوذ، ممیزی امنیتی، گواهی، ارزیابی حقوقی یا اثبات وجود کنترل‌ها نیست. هر کنترل باید با پیاده‌سازی و استقرار نهایی اعتبارسنجی شود.

اهداف: محرمانگی، یکپارچگی، دسترس‌پذیری، جداسازی Tenant، صحت مالی، ممیزی‌پذیری، حریم خصوصی، تاب‌آوری Provider و عملیات ایمن در حوزه‌های قضایی مختلف.

## ۲. دارایی‌ها
از هویت، عضویت، نقش، Credential API و Sessionهای Tenant؛ سلسله‌مراتب Affiliate/Agent، کمپین، Attribution و کمیسیون؛ کاتالوگ، سفارش، بلیت، شواهد نتیجه، مطالبه و تسویه Lottery؛ سند دفترکل، نگاشت حساب، فایل تطبیق و شواهد تأیید؛ داده شخصی و سوابق پشتیبانی/ممیزی؛ Credential Provider، Secret Webhook، کلید امضا/رمزنگاری و Secret استقرار؛ کد، Artifact، Workflow CI، وابستگی، Backup و Telemetry حفاظت کنید.

پیش از پیاده‌سازی داده‌ها را طبقه‌بندی کنید. مجاز بودن جمع‌آوری مدرک هویتی، Credential پرداخت یا داده حساس مشتری را فرض نکنید؛ ابتدا جمع‌آوری را حداقل و مبنای حقوقی و نگهداری را تعیین کنید.

## ۳. بازیگران و مرزهای اعتماد
بازیگران: کاربر نهایی، Affiliate/Agent، مدیر Tenant، اپراتور پلتفرم، پشتیبانی، Worker، سامانه شریک/Provider، هویت استقرار و سرویس ثالث.

مرزها: Client عمومی و Edge API؛ کاربر احرازشده و سرویس Tenant؛ سرویس Tenant و Control Plane مشترک؛ برنامه و Database/Cache/Object Storage/Queue؛ Callback و API Provider؛ Worker/Cron و Replay؛ ابزار پشتیبانی/مدیریت و دسترسی اضطراری؛ CI/CD/مخزن/Artifact/Runtime؛ Backup/Analytics/Observability/Export.

هر عبور از مرز، نقطه اعتبارسنجی و مجوزدهی است. موقعیت شبکه به‌تنهایی هویت نیست.

## ۵. جداسازی Tenant
Principal را احراز و سپس دسترسی Tenant را از Membership یا اتصال ماشینی معتبر حل کنید. شناسه Tenant، Agent، Account یا محصول ارسالی Browser/Partner بدون مجوزدهی سمت سرور قابل‌اعتماد نیست. Scope Tenant در APIهای Data Access اجباری باشد و در Database، Replica، Cache، Search، Object Storage، Export، Analytics، Log و Job پس‌زمینه اعمال شود. در صورت تناسب Unique Key و رابطه آگاه از Tenant تعریف کنید.

PostgreSQL RLS می‌تواند دفاع تکمیلی باشد، نه جایگزین مجوزدهی برنامه. Reset امن Context در Connection Pool و مرز Transaction تعریف و تست شود. Pool/Bridge/Silo بر اساس تهدید، قرارداد، مقیاس و مقررات انتخاب شوند؛ هیچ توپولوژی از پیش مصوب نیست.

تست منفی باید ثابت کند Tenant A قادر به خواندن، تغییر، استنباط، Export، دریافت Cache، ساخت Job یا دریافت Event متعلق به Tenant B نیست. دسترسی پشتیبانی پلتفرم فقط از مسیر اضطراری صریح و ممیزی‌شده مجاز است؛ Impersonation پنهانی ممنوع.

## ۶. امنیت API و Webhook
از TLS و سیاست مدرن Edge استفاده کنید. Credential و Scope هر Principal، Integration و محیط جدا باشد. مجوزدهی سطح Object و Function در همه Endpointها اعمال شود. Content-Type، Schema، اندازه، Encoding، Pagination و قواعد تجاری اعتبارسنجی شوند. Rate Limit بر اساس Tenant، Principal، Credential، IP/ریسک و عملیات پرهزینه باشد.

امضای Webhook باید Raw Body و Metadata لازم را پوشش دهد؛ Key ID، چرخش، مقایسه Constant-time، تحمل زمانی و Replay Protection لازم است. فقط پس از دریافت پایدار ACK بدهید؛ پردازش Async با Idempotency و Retry قابل مشاهده انجام شود. Stack Trace، Secret یا نشانه وجود داده Tenant دیگر افشا نشود.

## ۷. کنترل مالی و عملیات پرریسک
محاسبه، ثبت، تأیید، تطبیق، آغاز پرداخت و تأیید پرداخت جدا باشند. برای عملیات پرریسک Maker-checker، محدودیت مبلغ/سرعت، Audit تغییرناپذیر، Reason Code و تطبیق اعمال شود. موجودی Client یا Callback شریک به‌تنهایی مجوز انتقال ارزش نیست.

این مدل نگهداری وجه، پرداخت، توزیع جایزه یا عملیات پرداخت تنظیم‌گری‌شده را تصویب نمی‌کند.

## ۸. Secret و رمزنگاری
Secret در Secret Manager تأییدشده نگهداری شود؛ در مخزن، Log، Prompt، Ticket یا Bundle Client قرار نگیرد. Credential محیط‌های توسعه، تست، Staging و Production جدا باشند. در صورت توجیه از Envelope Encryption و KMS/HSM مدیریت‌شده استفاده و مالکیت، چرخش، ابطال، Backup و بازیابی کلید تعریف شود. گذرواژه با الگوریتم حافظه‌سخت روز و کتابخانه معتبر Hash شود. داده حساس در انتقال/سکون رمز و نگهداری حداقلی شود. در صورت امکان کلید امضا از Runtime جدا باشد. پیش از اتصال Provider فرایند چرخش/ابطال اضطراری تعریف شود.

## ۹. حریم خصوصی و حاکمیت داده
برای هر بازار فعال، موجودی داده، هدف، مبنای قانونی، حقوق صاحب داده، نگهداری/حذف، محل داده، انتقال برون‌مرزی، پردازشگر فرعی و اعلان نقض تعریف شود. در توسعه/تست از داده مصنوعی استفاده کنید. شناسه شخصی در Log/Analytics Mask یا Tokenize شود. پیش از تأیید نیاز محصول و حقوقی، مدرک هویتی یا Credential پرداخت جمع‌آوری نشود.

## ۱۰. توسعه امن و زنجیره تأمین
قابلیت مهم پیش از پیاده‌سازی Threat Model شود. با تصویب کنترل مخزن، Peer Review و Branch Protection لازم باشد. Dependency، Build Action و Base Image Pin و بازبینی؛ SBOM تولید و نگهداری شود. Source، Dependency، Secret، Container و تنظیمات زیرساخت اسکن شوند. در صورت پشتیبانی Artifact امضا/Attest شود. مجوز Build از Deploy جدا باشد. Migration سازگار با نسخه قبل بازبینی و راهبرد Rollback/Forward-fix تست شود. داده Production وارد محیط توسعه نشود.

## ۱۱. Log، تشخیص و پاسخ رخداد
Log امنیتی هویت Actor/Service، Scope Tenant، عملیات، مرجع هدف، تصمیم، نتیجه، زمان، Correlation ID و Context منبع را بدون Secret یا داده شخصی غیرضروری ثبت کند.

برای الگوی رد دسترسی بین Tenantها، تغییر مجوز، Export غیرعادی، شکست امضای Webhook، تعارض Replay، ناهنجاری Posting، شکست تطبیق، سوءاستفاده Credential و دسترسی غیرعادی پشتیبانی هشدار تعریف شود.

Runbook برای تصاحب حساب، افشای داده Tenant، نفوذ Provider، رخداد یکپارچگی دفترکل، افشای کلید، Ransomware، فقدان داده و قطعی آماده شود. مهار، حفظ شواهد، تصمیم اعلان، بازیابی، بازبینی پس از رخداد و بهبود کنترل‌ها را پوشش دهید. بازیابی Backup آزمایش شود.

## ۱۲. ماتریس حداقلی راستی‌آزمایی
پیش از ادعای آمادگی Production لازم است: تست جداسازی Tenant در API/DB/Cache/Storage/Queue/Analytics/پشتیبانی؛ تست مجوز Object/Function/Field؛ تست امضا/Replay/Timestamp/Duplicate/چرخش Webhook؛ تست Idempotency مالی هم‌زمان، تراز و معکوس‌سازی؛ تست Maker-checker و Audit؛ شواهد Secret Scan و Dependency/SBOM؛ تمرین Restore و Disaster Recovery؛ تست Rate Limit/Abuse/Exhaustion؛ تست نگهداری/حذف/Export حریم خصوصی؛ و تست نفوذ مستقل و اصلاح متناسب با ریسک و بازار.

## ۱۳. پذیرش ریسک و تصمیم‌های باز
هر ریسک باقیمانده High/Critical باید مالک، دلیل، کنترل جبرانی، تاریخ انقضا/بازبینی و پذیرش صریح داشته باشد. تصمیم‌های باز: حوزه‌های قضایی اولیه، سطح اطمینان هویت، مدل پشتیبانی، محل داده، نگهداری، طراحی KMS/HSM، توپولوژی جداسازی، تعهد اعلان رخداد، الزامات اعتماد Provider و مرز پرداخت/نگهداری.

این سند گواهی یا اثبات پیاده‌سازی کنترل‌های امنیتی نیست.
