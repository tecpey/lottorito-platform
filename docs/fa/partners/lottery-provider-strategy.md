# راهبرد ارزیابی و اتصال ارائه‌دهندگان Lottery در Lottorito

**شناسه سند:** LOT-LOT-INT-001 | **نسخه:** ۰.۱.۰ | **وضعیت:** چارچوب ارزیابی؛ هیچ ارائه‌دهنده‌ای انتخاب یا تأیید نشده است  
**مرتبط با:** LOT-LOT-PRD-001 و LOT-LOT-ARCH-001

## ۱. هدف

روش تکرارپذیری برای ارزیابی، قرارداد، اتصال و بهره‌برداری از ارائه‌دهندگان بیرونی Lottery تعریف می‌شود؛ بدون وابسته‌کردن هسته Lottorito به یک تأمین‌کننده.

این سند هیچ ارائه‌دهنده‌ای را انتخاب، تأیید، توصیه رسمی، طرف قرارداد، گواهی‌شده یا یکپارچه‌شده اعلام نمی‌کند. وب‌سایت و مستندات API عمومی صرفاً شواهد اولیه‌اند و بررسی حقوقی، تجاری، امنیتی، فنی و عملیاتی همچنان الزامی است.

## ۲. پیش از مقایسه، نوع ارائه‌دهنده را مشخص کنید

هر فروشنده ابتدا باید به یک یا چند کلاس قابلیت منتسب شود:

| کلاس | قابلیت‌های معمول | چیزی که اثبات نمی‌کند |
|---|---|---|
| API داده و نتایج Lottery | کاتالوگ بازی، زمان‌بندی، نتیجه قرعه‌کشی، تاریخچه، Jackpot و اصلاحات | فروش بلیت، اداره بازی یا پرداخت جایزه |
| تأمین‌کننده بازی/محتوا | تعریف بازی، محتوا، RNG/موتور بازی یا سرویس قرعه‌کشی | مجوز اپراتور، جذب مشتری، پرداخت یا تسویه |
| API صدور بلیت / تراکنش | ایجاد بلیت، پذیرش، وضعیت، لغو و رسید | پوشش گسترده کاتالوگ یا مجوز قانونی در همه بازارها |
| پلتفرم Turnkey Lottery | چند گردش‌کار اپراتوری، مدیریت و رابط مشتری | قابلیت انتقال، مجوز مستقل یا تناسب با همه حوزه‌های قضایی |
| ارائه‌دهنده پرداخت / هویت / موقعیت | یک کنترل پشتیبان مشخص | جایگاه ارائه‌دهنده Lottery یا اختیار اداره آن |
| اپراتور رسمی / شریک دارای مجوز | عملیات مجاز در بازار مشخص | اختیار خارج از قلمرو مجوز یا قرارداد |

ممکن است فروشنده چند کلاس را پوشش دهد؛ هر قابلیت باید مستقل از بقیه اثبات شود.

## ۳. چشم‌انداز اولیه مبتنی بر منابع عمومی

موارد زیر نقطه شروع تحقیق‌اند، نه فهرست کوتاه رتبه‌بندی‌شده یا تأییدشده:

- **Lottevo:** مستندات عمومی، REST API نسخه‌بندی‌شده برای کاتالوگ، زمان‌بندی، نتایج قرعه‌کشی، داده تاریخی، بررسی بلیت در برابر نتایج گذشته، Feed تغییر/Revision، شاخص کیفیت داده و تحویل رویداد را توصیف می‌کند. وب‌سایت عمومی آن اعلام می‌کند سرویس داده Lottery است و فروشنده بلیت یا اپراتور نیست. تا پیش از قرارداد و اعتبارسنجی سرویس، فقط نامزد بررسی برای Adapter داده/نتایج تلقی شود.
- **Lottery Results API:** مستندات عمومی، API تعاملی Swagger و Endpointهایی برای جست‌وجوی Lottery و نتایج نشان می‌دهد. محتوای عمومی آن را سرویسی داده/نتیجه‌محور معرفی می‌کند. پوشش، دقت، فرایند اصلاح، سطح خدمت، مجوز داده و حقوق تجاری نیازمند راستی‌آزمایی مستقل‌اند.
- **new-lotto.net/api.php:** پیش‌تر به‌عنوان URL مرجع ارائه شده است. Schema فعلی API، هویت اپراتور، مجوز، دامنه سرویس، احراز هویت، دسترس‌پذیری و شرایط تجاری آن در این بررسی تأیید نشده‌اند. از URL یا یک پاسخ نمونه، قابلیت را استنباط نکنید.
- **تأمین‌کنندگان بزرگ فناوری Lottery و اپراتورهای محلی دارای مجوز:** ممکن است پلتفرم سازمانی، قرعه‌کشی، خرده‌فروشی، دیجیتال یا سرویس مدیریت‌شده را از طریق مناقصه و قرارداد خصوصی عرضه کنند، نه API عمومی Self-service. وب‌سایت عمومی اثبات وجود API یا برنامه همکاری نیست.

API داده و پلتفرم Ticketing را محصولاتی هم‌ارز مقایسه نکنید.

## ۴. چک‌لیست Due Diligence

### ۴.۱. شرکتی، حقوقی و تجاری

- شخصیت حقوقی طرف قرارداد، مالکیت ذی‌نفع نهایی، سابقه فعالیت و ثبات مالی.
- نقش دقیق: مجوزدهنده داده، تأمین‌کننده فناوری، پردازشگر Ticketing، اپراتور، Reseller یا پیمانکار فرعی.
- بازارها و بازی‌های تحت پوشش؛ محدودیت قلمرو و شرایط احراز صلاحیت مشتری.
- مجوزهای لازم اپراتور/تأمین‌کننده، گواهی‌ها، تأیید نهاد ناظر و ممیزی مستقل.
- حقوق مالکیت فکری داده، محتوای بازی، بلیت، نتیجه و برند.
- فهرست Subprocessorها، پیمانکاری فرعی، محل داده و انتقال برون‌مرزی.
- مدل تجاری، حداقل تعهد، Revenue Share، کارمزد تراکنش، مالیات، بازپرداخت و حق فسخ.
- بندهای انحصار، عدم رقابت، White-label، Sublicense و قابلیت انتقال.
- کمک خروج، Export داده، گواهی حذف و تداوم سرویس.

### ۴.۲. API و فنی

- مستندات کامل OpenAPI/Swagger یا معادل و سیاست نسخه‌بندی.
- دسترسی Sandbox، Fixtureهای تست، هویت‌های آزمایشی و سناریوهای قطعی.
- احراز هویت، Scope کلید، اعتبارسنجی امضا، چرخش کلید و Replay protection.
- مدل کاتالوگ/قواعد بازی، شناسه پایدار و اعلان تغییر.
- قابلیت Quote، ارسال بلیت، Idempotency، استعلام، لغو و Refund.
- منبع نتیجه، تأخیر انتشار، وضعیت‌های provisional/confirmed/corrected و تاریخچه Revision.
- تضمین تحویل Webhook، سیاست Retry، ترتیب، Cursor/Replay و Dead-letter.
- صفحه‌بندی، Rate limit، Quota، محدودیت Payload، طبقه‌بندی خطا و Correlation ID.
- دقت ارز، منطقه زمانی، DST، بومی‌سازی و نگهداری تاریخچه.
- دسترس‌پذیری، تأخیر، پنجره نگهداری، اعلان رخداد و مسیر Escalation.
- تست امنیتی، افشای آسیب‌پذیری، تست نفوذ و اطمینان مستقل.
- Export و Portability داده، بازیابی بحران، Backup، RPO/RTO و تداوم کسب‌وکار.

### ۴.۳. عملیاتی و مالی

- Merchant/Operator of Record کیست و چه کسی شرایط مشتری را می‌پذیرد؟
- چه کسی مسئول پذیرش بلیت، وجوه مشتری، بدهی جایزه، Claim و تصمیم پرداخت است؟
- کدام طرف مرجع وضعیت بلیت، زمان‌بندی، نتایج، اصلاحات و تسویه است؟
- قالب صورت‌حساب تسویه، دوره، ارز، Cutoff، کارمزد، مالیات و حل مغایرت.
- گردش‌کار اختلاف، Chargeback، Refund، لغو و جایزه مطالبه‌نشده.
- ارجاع‌های تطبیق برای اتصال رکورد ارائه‌دهنده به سفارش، بلیت و اثر دفترکل Lottorito.
- مسئولیت پشتیبانی دستی و مالکیت رخداد.

## ۵. مدل ارزیابی وزن‌دار

هر معیار از ۰ تا ۵ همراه با مدرک و یادداشت بازبین امتیاز می‌گیرد. امتیاز کل بالا نمی‌تواند شکست در دروازه حقوقی، مجوز، امنیت، یکپارچگی یا کنترل مالی را جبران کند.

| بُعد | وزن |
|---|---:|
| مجوز حقوقی، وضوح نقش و تناسب بازار | ۲۰٪ |
| قابلیت API و کیفیت قرارداد | ۱۵٪ |
| یکپارچگی بلیت/نتیجه و قابلیت ممیزی | ۱۵٪ |
| امنیت، حریم خصوصی و اطمینان مستقل | ۱۵٪ |
| تاب‌آوری عملیاتی و پشتیبانی | ۱۰٪ |
| تسویه مالی و تطبیق | ۱۰٪ |
| شرایط تجاری، قابلیت انتقال و خروج | ۱۰٪ |
| پوشش، بومی‌سازی و تناسب نقشه راه | ۵٪ |
| **مجموع** | **۱۰۰٪** |

مقیاس امتیاز: ۰ = غایب/مردود؛ ۱ = شکاف جدی؛ ۲ = ناقص با شروط مهم؛ ۳ = حداقل شواهد لازم را دارد؛ ۴ = قابلیت قوی و راستی‌آزمایی‌شده؛ ۵ = مستقلانه اثبات و قراردادی متعهد شده است. «نامشخص» امتیاز ۳ نیست؛ با وضعیت **راستی‌آزمایی‌نشده** ثبت و برای آن مدرک درخواست شود.

### دروازه‌های توقف قطعی

تا زمان حل موارد زیر، وارد خرید Production یا اتصال زنده نشوید:

- نقش حقوقی و مجوز بازار.
- حقوق عرضه بازی/داده و فروش مجدد یا نمایش آن.
- مدل امنیت و احراز هویت.
- Idempotency ارسال بلیت و بازیابی نتیجه نامعلوم، اگر Ticketing در محدوده است.
- منشأ نتیجه و تاریخچه اصلاح، اگر نتیجه بر اعتبارسنجی یا تسویه اثر دارد.
- مسئولیت صورت‌حساب مالی و تطبیق، اگر پول در محدوده است.
- تعهدات حفاظت داده، نگهداری و رخداد.
- قرارداد اجرایی، SLA پشتیبانی و حقوق خاتمه/انتقال.

## ۶. الگوی یکپارچه‌سازی

۱. **کشف:** هویت فروشنده، کلاس قابلیت، بازار/بازی پشتیبانی‌شده، لینک شواهد و پرسش‌های باز ثبت شود.  
۲. **Due Diligence:** بازبینی حقوقی، تجاری، امنیتی، فنی، مالی و عملیاتی تکمیل شود.  
۳. **خط مبنای قرارداد:** نسخه API، مدل اعتبارنامه، Schema رویداد، SLA، حقوق داده و مسئولیت‌ها تثبیت شود.  
۴. **پیاده‌سازی Adapter:** فقط قابلیت‌های تأییدشده به قراردادهای Canonical نگاشت شوند؛ شناسه منبع و شواهد حفظ شوند.  
۵. **راستی‌آزمایی Sandbox:** تست قرارداد، Duplicate/Replay، بازیابی Timeout، اصلاح نتیجه، جداسازی Tenant و Fixture تطبیق اجرا شود.  
۶. **پایلوت کنترل‌شده:** بازار، اپراتور، بازی، حساب آزمایشی و سقف تراکنش مصوب با مالک رخداد مشخص استفاده شود.  
۷. **تأیید Production:** دروازه‌های Compliance، امنیت، مالی، عملیات و محصول امضا شوند.  
۸. **اطمینان مستمر:** تازگی، کامل‌بودن، نرخ خطا، Drift، مغایرت تسویه، تغییر فروشنده و نقض SLA پایش شوند.

## ۷. تاب‌آوری و سیاست چندارائه‌دهنده‌ای

- امکان پیکربندی چند ارائه‌دهنده برای هر قابلیت و بازار وجود دارد؛ Failover عمومی و خودکار فرض نشود.
- برای هر تراکنش فقط یک ارائه‌دهنده مرجع Ticketing تعریف شود. یک خرید را به‌عنوان Failover خودکار به دو ارائه‌دهنده ارسال نکنید.
- در ارسال نامعلوم بلیت، ابتدا نتیجه ارائه‌دهنده اصلی تعیین تکلیف شود و بعد مسیر جایگزین بررسی شود.
- Fallback منبع نتیجه باید صریح، رتبه‌بندی‌شده، دارای Timestamp و قابل مشاهده باشد؛ نتایج متناقض وارد گردش‌کار اختلاف شوند.
- Rate limit، Circuit breaker، اعتبارنامه، صف و سیگنال سلامت اختصاصی هر ارائه‌دهنده حفظ شود.
- مهاجرت ارائه‌دهنده به نگاشت داده، تطبیق، ردیابی تاریخی و برنامه Cutover مصوب نیاز دارد.
- Provider-neutral یعنی قرارداد قابل جایگزینی و Adapter کنترل‌شده؛ نه قابلیت‌های یکسان یا جابه‌جایی بی‌اصطکاک.

## ۸. نتیجه تحقیق و مدارک بعدی

منابع عمومی بررسی‌شده از یک گام روشن پشتیبانی می‌کنند: جداسازی منبع داده/نتیجه از Ticketing تراکنشی و عملیات Turnkey. بر اساس توصیف API عمومی، Lottevo نامزد قابل بررسی برای داده/نتایج است؛ اما مدرکی برای راهکار Ticketing یا اپراتوری نیست. Lottery Results API و مرجع new-lotto ارائه‌شده باید پیش از هر تصمیم فهرست کوتاه، در سطح Endpoint و قرارداد راستی‌آزمایی شوند.

پیش از انتخاب ارائه‌دهنده، این مدارک را دریافت کنید:

۱. شخصیت حقوقی و شرح نقش.  
۲. مشخصات کامل API/OpenAPI و سیاست نسخه‌بندی.  
۳. اعتبارنامه Sandbox و Fixtureهای تست از کانال مجاز.  
۴. بازارها، بازی‌ها، حقوق و اعلام مرجع حقیقت.  
۵. مستند چرخه بلیت و Idempotency، در صورت ارتباط.  
۶. منشأ نتیجه، سیاست اصلاح و اختلاف.  
۷. بسته امنیتی، شرایط پردازش داده و فهرست Subprocessorها.  
۸. نمونه صورت‌حساب تسویه، تعرفه و مشخصات تطبیق.  
۹. SLA، Escalation پشتیبانی، رخداد و حقوق خروج/انتقال.

## ۱۰. وضعیت

هیچ ارائه‌دهنده‌ای انتخاب یا تأیید نشده است. هیچ اعتبارنامه API، Sandbox، اتصال، گواهی، توافق تجاری یا آمادگی Production ادعا نمی‌شود. این سند فقط با دریافت و بازبینی شواهد جدید به‌روزرسانی شود.
